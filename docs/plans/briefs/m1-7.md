# M1-7 · Chat with an agent from the terminal

Design review against Spindle `a593851` (M1-6) and spec `f462a673297faed1f849ef1741ddda1e06b6c817`. A reviewer wrote this brief and the 33 tests in `packages/runtime/test/cli/chat*.test.ts` before the build. The owner implements until they pass, and records the reason in the PR for any test the owner changes. Citations are relative to `content/0.2.0/`. **R** = `infrastructure/runtime.md`, **E** = `specification/threads/execution-state.md`, **M** = `specification/threads/messages.md`, **T** = `specification/threads.md`. **O** is a line of part 2 and **F** is a row of part 3.

## 1. What the spec requires, and what replaces the plan

The spec has no chat command. Seven statements bind what chat does. Everything else here is Spindle's own design.

- R:33,38. A line is a user message trigger. It goes through the queue, and a thread that is executing queues it.
- R:239,388. One thread never executes two flows. Chat waits behind a holder and never starts beside one.
- E:63. Stop ends the execution after the current operation. R:231 gives the abort to terminate only.
- E:107 to 109,118 to 120. Chat prints the raw reason code and leaves no thread `running` at an orderly exit.
- R:92. A tool error is a stored result, and the run goes on. R:229 to 232. A terminated thread rejects every send.
- M:127. A client hides a silent message. M:159,160. A line takes the role of the human side, so chat reads both roles from the agent.
- T:236. A secret value is redacted from tool output and logs.

These decisions are newer than the plan section and replace it where they differ.

|Plan words|Replacement|
|---|---|
|"Ctrl-C during a run calls `execution.stop()` and returns to the prompt"|The first Ctrl-C asks for a cooperative stop. The operation in flight finishes, its result is stored, and no abort signal fires. The second Ctrl-C in the same run aborts it.|
|No words on a tool that ignores an abort|The abort holds the thread until that tool returns. The prompt returns at once, and a line typed then waits in the queue with O11. A tool that never returns holds the thread until the process exits.|
|"Read lines through the Effect `Terminal` service", and the file boundary|Chat needs line input from a pipe, a test for a terminal, a write with no newline, and a closed-output error. These belong under `src/platform/`, which the boundary leaves out.|
|"Verify, unit" with a test `Terminal` layer|The tests run the real command in a child process, from source as `queue.test.ts` does, because CI tests before it builds `dist`. Two of them use a pseudo-terminal through `test/cli/terminal.py` and need `python3`.|
|Flags `--dir`, `--db`, `--script`, `--thread`|Lanes 2 and 7 need `--dump-requests`. Chat takes it and `--trace` as `spindle run` does.|
|"Verify, perf" rule|Reported and not gated. One check stays. The first prompt shows within 5 seconds of process start.|

## 2. The output contract

Standard output holds the conversation. Standard error holds notes, and each starts with `spindle: ` at the start of a line. Chat prints nothing while it waits at the prompt, and nothing at exit but a newline, O13, and O14. A resumed chat prints no history. Every line passes the redactor when it prints, the echo of a typed line included. Then each control character except a newline or a tab prints as `\x` and two hex digits. Exit code 0 follows end of input or Ctrl-C at the prompt. Exit code 1 follows a start failure, a terminated thread, or closed output.

|Id|When|Line|
|---|---|---|
|O1|Start, before the first prompt|`spindle: thread <id>`. With no `--db` a second line reads `spindle: no --db, so the thread lives in memory and ends with this chat`.|
|O2|Start with `--thread`|`spindle: <state> (<reason>)`, or `spindle: running in process <pid>, so a line you type waits in its queue`.|
|O3|Ready for a line|`> ` with no newline. When input is not a terminal, chat prints the line it read and a newline.|
|O4|Message of the prompt side|Its text. A silent message prints nothing.|
|O5|Tool call|`[tool call] <name> <arguments as one line of JSON>`|
|O6|Tool result|`[tool result] <name> ok: <stored content>` on one line, or `[tool result] <name> ok` for empty content. Show the first 200 printed characters and append `...` when more follow. With `--full-results` show all of them. An error prints `[tool result] <name> error: <stored content, each newline as a space>`|
|O7|Human-side message that this chat did not send. A hook seeded it, another process sent it, or an earlier chat left it queued.|`[elsewhere] <text>`|
|O8|First Ctrl-C in a run|`spindle: stopping after the current operation. Press Ctrl-C again to abort.`|
|O9|Second Ctrl-C in a run|`spindle: aborting the run`. The prompt returns without waiting for the run.|
|O10|A run settles with a reason other than `stop_on_response`|`spindle: <state> (<reason>)`, after the run's records. A failed run first prints `spindle: provider error: <message>` when the error's origin is a provider, and `spindle: error: <message>` otherwise.|
|O11|A line waits behind a holder|`spindle: thread <id> is running in process <pid>, so the line waits in its queue`, or `spindle: tool <name> has not returned since the abort, so the line waits in the queue until it does`.|
|O12|A line could not be admitted|`spindle: the line was not sent: <cause>`. Nothing is stored and the prompt returns.|
|O13|Exit while a sent line is still queued|`spindle: your last line is still queued, and the next run of the thread delivers it`|
|O14|Exit, last line, for a thread in a file that is not terminated|`spindle: resume with spindle chat <agent> --thread <id> --db <db>`, then ` --dir <dir>` when it was given. A value that the shell would split is wrapped in single quotes.|
|O15|Start failure, exit 1, no thread and no prompt|The lines `spindle run` prints for definition errors, an unknown agent, and a database that cannot be opened. `spindle: no thread <id> in <db>`. `spindle: thread <id> is terminated, so it takes no new message, queued work, or execution`. `spindle: thread <id> belongs to agent <a>, not <b>`. `spindle: --thread needs --db`.|
|O16|Standard output closes|`spindle: standard output is closed`, then O14, exit 1.|

## 3. What can go wrong at each step

**B** marks a row that blocks by part 4. **n** marks a row that goes to the follow-up file.

|Id|Step and failure|What the command must do|Gate|
|---|---|---|---|
|F01|Start. Definition errors, an unknown agent, an unreadable database|O15. Create no thread.|n|
|F02|Open. `--thread` is missing, terminated, or of another agent|O15. Change nothing in the database.|n|
|F03|Open. `--thread` runs in a live process|O1, O2, and the prompt. A typed line waits with O11. Its reply prints whichever process made it. No second execution starts.|B|
|F04|Open. The holder of `--thread` is gone|Repair as any observer does. O2 reads `failed (execution_lost)`. The repair's records are history and do not print. The next line runs, and no tool runs again.|B|
|F05|Read. End of input or Ctrl-C at the prompt|A newline, O14, exit 0.|B|
|F06|Read. An empty line, or one of spaces only|Send nothing. Prompt again.|n|
|F07|Read. A very long line, or one with a control character|Store it whole and as typed, as one message. Only the printed copy is escaped.|B|
|F08|Read. Several lines arrive at once, or during a run|One line is one turn, in order. Chat reads only at the prompt and drops no line.|B|
|F09|Read. Input is a terminal|No second echo. Ctrl-C and Ctrl-D typed as keys act as F05 and F15 say.|B|
|F10|Send. The database stays locked past the driver's 5 seconds, or the write fails|O12. The next line works.|B|
|F11|Send. Another process terminated the thread|The terminated line of O15, exit 1, no O14.|n|
|F12|Print. A secret in a reply, call arguments, an error, or a typed line|`[redacted]` on the terminal. The stored human and model text stays as written.|B|
|F13|Print. A record is stored|It prints before the next operation ends, so a call line shows while its tool runs. Each record prints once, in stored order.|n|
|F14|Run. End of input arrives during a run|The run finishes and its records print. Then F05.|B|
|F15|Run. First Ctrl-C|O8. The tool or model call finishes with no abort, and its result is stored. No further model call. O10, the prompt, and the next line gets a reply.|B|
|F16|Run. Second Ctrl-C, and the tool watches the signal|O9. The open call gets one error result. The next line prints the closing records, O10, and its reply.|B|
|F17|Run. Second Ctrl-C, and the tool ignores the signal|O9 and the prompt. The thread stays `running`. A typed line gets O11 and waits. When the tool returns, its call has one error result, its late return is dropped, it does not run again, and the line runs.|B|
|F18|Run. A tool never returns|Three Ctrl-C always end the command, since the third is at the prompt. The exit settles the thread, and a resumed chat gets a reply.|B|
|F19|Run. Ctrl-C while a line waits behind a holder|O13, O14, exit 0. The line stays queued once.|B|
|F20|Run. A tool throws|O6 with the error. The run goes on. Every call line has one result line.|B|
|F21|Run. The provider is down or answers with an error|O10. The human line stays stored. The next line, or a resumed chat, gets a reply.|B|
|F22|Run. `spindle send` from another process during this chat's run|This run takes the message before its next model call and prints O7. The other process makes no provider request.|B|
|F23|Run. `spindle send` from another process while this chat is at the prompt|Chat prints nothing then. The next line prints the records it missed, O7 first, before its own reply.|n|
|F24|Run. `spindle recover --force` takes the thread|O10 reads `failed (execution_lost)`. The prompt returns.|n|
|F25|Print. Standard output closes|Stop the run cooperatively and settle it. O16 on standard error, exit 1, no stack trace.|B|
|F26|Exit. The database file was deleted during the chat|No O14. `spindle: the database <db> is gone`, exit 1.|n|
|F27|Exit. SIGTERM, a closed terminal, or SIGKILL|An orderly exit settles the run. A killed process leaves the repair of F04 to the next observer.|n|

## 4. Which failures block

A finding blocks when stored data is lost or changed, a secret leaks, a tool call has no result or a result has no call, a tool runs twice, two executions of one thread run at once, or a thread cannot continue. A command that a person types adds one more. The command hangs with no message, or it exits without O14 when the thread can be resumed. A row is marked **B** when a wrong build of it produces one of these. Every other finding goes to `docs/plans/trail/m1-followups.md`.

## 5. The seam in the supervisor

The tests need four things from `ThreadSupervisor` and the store. The owner chooses their shape. No test names a symbol of the seam.

1. The messages a thread committed after a given sequence, in order, whichever process committed them. Chat prints from this, so that F03, F22, and F23 show a reply that another process made. A record of a run in this process arrives before the next operation ends (F13).
2. A way to tell the record of a line this chat sent from another human-side record, such as the sequence of its admission.
3. An abort that returns at once, a settlement that chat can await later, and the name of the tool that an aborted run still waits for (F17).
4. A send that reports that it waits and why, before it waits. Today `observe` reports only a holder in another process.

## 6. Open questions for the lead

The tests follow each recommendation.

1. **What does chat do with no `--db`?** The plan's example resumes a chat that named no database, which needs a default file. Recommend the meaning `spindle run` has. The thread lives in memory, O1 says so, and no resume line prints.
2. **Does a piped transcript show the prompt and the typed line?** Recommend yes, by O3. A saved transcript then reads like the session, and a test can wait for a prompt.
3. **May model and tool text drive the terminal?** Recommend no. Control characters print escaped, and the stored text is unchanged.
4. **When does the prompt return after an abort?** Recommend at once, with the closing records at the next line. The other choice is a timer that guesses whether the tool will return.
5. **What is the exit code when output closes?** Recommend 1, because the command could not go on.
6. **Does O6 hide the content of a successful result?** On 2026-11-26 the operator chose to show the stored result as specified in O6.
