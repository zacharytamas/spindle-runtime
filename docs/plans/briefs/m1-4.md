# M1-4 · One prompt side, one human side

Plan: `docs/plans/m1-core-loop.md` at `8c2c209787c05ad4760376fe7644df7f857de09c`. Spec paths below are relative to `content/0.2.0` at `f462a673297faed1f849ef1741ddda1e06b6c817`. Declaration lines (“D”) refer to `packages/runtime/node_modules/@standardagents/spec/dist/index.d.ts`, version 0.45.13.

## 1. Corrections to the build and evidence boxes

1. **History has two perspectives.** Plan 304 “convert the history to provider messages” and 328 “one user message and one assistant message” do not check authorship. “A human on side A is legal” and “role: 'user'” is B's perspective (specification/agents.md:63–64). For human A, persist inbound as assistant and model B as user. Present them as user and assistant respectively to B, including B’s calls and reasoning. Keep tool results linked by call ID. Test both orientations. Hide opposite-side calls (infrastructure/runtime.md:77–80).
2. **Replay is as important as capture.** Plan 305 “persist the assistant message with its reasoning fields”; specification/threads/messages.md:74–77 says “in a form the selected provider and model accept” and “The persisted record is not altered.” Decode structured details on replay, condition by eligibility, prompt inclusion and model compatibility. Absence of text and absence of details are independent. D1140–1185 permits details on finish despite specification/providers.md:390 omitting them.
3. **Argument types change twice.** Plan 306 “validate the model's arguments against the schema”; specification/threads/messages.md:17 says “where `arguments` is itself JSON-encoded”; specification/providers.md:387 says “arguments: Record<string, unknown>”. Preserve the function envelope and raw argument string where available, reconstruct the provider object for valid history, run the declared schema on the parsed object and give the tool its parsed output. An invalid wire JSON string cannot inhabit a typed done chunk. Lane 9 checks only well-formed but invalid arguments. Exercise malformed JSON at the adapter boundary and design its error path explicitly (part 5).
4. **The coverage box overclaims.** Plan 324 “sections 4.2 and 5.2, change to `covered`”; specification/prompts.md:205 says “when the prompt is called as a tool”. Its requiredSchema conversion, validation and field descriptions at 216–220 need M2 prompt-tool evidence. Validate untrusted prompt inputs at 222 now. Function args have their own requirement at specification/tools.md:152. Also test annotations at 145–146,156. Plan 322’s runtime §§3–6 alone omit these and message/provider contracts.
5. **Assemble eligible history.** Plan 304 “convert the history” leaves out “Include full chat history” and “Include past tool results”, both default false (specification/prompts.md:26–27). Preserve the active exchange, chronological order, silent eligibility, multimodal content, image aging and tool links; explicitly test prior turns with flags on/off (infrastructure/runtime.md:65–82; specification/prompts.md:252–255). An ordinary default message listing is descending and hides silent rows.
6. **Resolve the whole request.** Plan 308 “Pass `toolChoice` through” omits “Implementations **SHOULD** retry if the LLM fails to call a tool” (specification/prompts.md:194). “An explicit `parallelToolCalls` value controls the provider option” (38), independently of sequential local execution. Carry native model ID, exposed function schemas, merged options and reasoning settings; level zero is meaningful (specification/providers.md:245–264). Keeping definitions with none in lane 7 is a valid Spindle choice, optional in the spec.
7. **Two provider methods and a transport contract.** Plan 303/309 “against `LLMProviderInterface`” needs both “Non-streaming generation. Returns complete response” and streaming (specification/providers.md:34–35). Exercise both on both providers, although the loop uses stream. Honor injected fetch on every backend call, forward default headers, declare the credential secret, attribute provider errors, and handle optional post-response metadata (specification/providers.md:56–63,423–428,563–566; infrastructure/providers.md:136–139,182–189,205–212). A recorded standard request cannot prove the adapter’s native mapping.
8. **Hello World’s model is fixed.** Plan 311 “Change only the provider import” versus plan 309’s test model. The example literally selects “model: 'anthropic/claude-sonnet-5'” (getting-started/examples.md:35); “The model identifier sent to the provider API” is the definition’s model (specification/models.md:19). Alias the import if retaining the old binding; allow the live fixture to select the lane model explicitly. Do not silently substitute an environment-selected model inside every provider request.
9. **Check what actually stopped.** Plan 331 “exactly one request” also passes on premature failure or an unrelated cap. “Stop side turn when this tool is called” and “Extracted property for stop tool outcomes” (specification/agents.md:42–43). Verify the named call's result and any siblings persisted before stopping; distinguish the winning reason via public outcome. Plan 332’s “step-limit reason” needs a public observation before M1-6 owns durable statuses. A stopTool and a true response-stop predicate cannot coincide (41); test mixed text/calls as a negative case.
10. **Result shape and failure isolation.** Plan 307 “Persist a tool error as a tool result” and lane 3 omit recoverable failures followed by another call in the *same* response. “Tool errors **MUST** be persisted as tool results and **MUST NOT** crash the execution loop” (infrastructure/runtime.md:92). Correlate name, ID and status even for unexposed names, validation failures and throws; preserve status-only results and attachment references. A provider failure is a different boundary (specification/providers.md:394–409).
11. **Make per-tool durability observable.** Plan 289/317 “tools, persist-results” and lane 2 “first result persisted before the second tool starts”. The numbered list says “Execute tool calls sequentially” then “Persist tool results” (infrastructure/runtime.md:48–49), while §16 says “persist messages/tool results before advancing” (387). The assistant’s separate commit is unambiguous. Keep lane 2’s stronger per-result rule and read the row through a separate reader while the next tool is blocked. A trace label or a shared KV read cannot establish commit timing.
12. **Includes and variables are not simple concatenation.** Plan 335 “holds the included text and the variable's value”. “Only the `prompt` field is included” (specification/prompts.md:91); recursively expand in place and reject cycles (88–90), apply env precedence (specification/threads.md:220–225), validate input and sanitize untrusted substitutions. “System prompts **MUST NOT** contain secrets” (specification/prompts.md:50). Lane 8 should include conflicting defaults, nested content and a non-secret variable. Redact secrets in plan 312’s “prints each provider request as JSON”.
13. **The driver has evidence limits.** Plan 302 “reads messages, and returns the provider requests” cannot distinguish two matching stop reasons, retry attribution, or log-only metadata updates. “Results update log records with provider-reported metadata” (specification/providers.md:566). Expose the public run outcome and scripted provider observations, and check log/transport evidence separately. Avoid equating request counts with reason precedence or storing log fields as new mandatory message columns.

## 5. Open readings and decisions

1. **Malformed wire JSON.** specification/providers.md:385–391 permits argument fragments and only an object on done; it offers no per-call parse-error variant. Options are provider-level failure or a correlated invalid-call outcome. Prefer the latter for identifiable local calls, preserving raw bytes for diagnostics and satisfying infrastructure/runtime.md:92. A forged object/dummy successful completion is unsafe. Operator must settle the adapter/runtime boundary and how invalid history is presented to a provider whose argument shape requires an object.
2. **Missing details on the published stream.** specification/providers.md:390 has finish reason/usage only; D1140–1185 adds finish.reasoningDetails, per-call extraContent, provider-tool-done and web-search-done. Use typed finish details to satisfy specification/threads/messages.md:73–77. Preserve opaque data needed for a compatible follow-up; provider-executed events are informational, never execute them as local calls (D1008–1025). For encrypted formats without a known conversion, omit incompatible details on dispatch. Empty returned details versus none should be preserved when distinguishable.
3. **Partial/empty streams.** specification/providers.md:348–353,380–391 defines variants, no grammar for duplicate IDs, conflicting final/deltas, EOF without finish, empty content-done or error after deltas. Recommend first appearance for call order, done object authoritative for a well-formed call, finish once per complete cycle. Abort incomplete/unrecoverable streams without executing partial calls. Null/empty/whitespace text, reasoning-only, content_filter/length and finishReason error require explicit public policy. Prefer text-stop only for substantive text with zero calls and bounded repeated empty steps. Persist completed empty cycles distinctly from failed partial responses. Operator chooses partial-record and whitespace policy.
4. **Two meanings of history.** specification/prompts.md:26–27,168 gives flags but leaves “past” and handling of call/result pairs imprecise. Prefer previous human turns as historical boundary, current triggering input and current cycle’s matched tool exchanges available even with defaults false, exclude stale result/call pairs together. D4416–4430 adds historyLimit that windows *execution history* too; specification/threads/execution-state.md:45–51 requires live chronological persisted history and separates request snapshots. Leave this type-only optimization off unless operator defines behavior. Excluding old messages must remove their reasoning.
5. **Rich tool results and attachments.** D211–245 allows independent optional result, error, error_code, error_data, stack, attachments; Message (specification/threads/messages.md:15–29) defines status, content, refs, metadata but no canonical rich-error layout. Prefer error for model-facing error text, retain structured diagnostics via protected metadata or logs, avoid stack leakage. Expose full direct result to calling tool. Fresh ToolAttachment requires a real file write and resulting ref; existing references require no copying in the same thread. Operator must choose a minimal attachment dependency now or explicitly defer byte materialization to M3 with an observable capability error. Never claim new-file success from storing base64 in a ref. Similar gap for generated image chunks and image descriptions without a filesystem (infrastructure/runtime.md:82; specification/prompts.md:254–255).
6. **Stop outcome extraction.** specification/agents.md:42–43 says “when this tool is called” and “Extracted property”; D4824–4836 specifies the tool’s *result*, whereas session bindings explicitly use argument fields. Prefer a result field, not an argument lookup. ToolResult.result is itself an optional string; the text does not prescribe parsing JSON, nested paths, multiple stop calls, absent property or a failed stop call. Prefer first named call in returned order, save every sibling, treat failure as a result; invocation still matches by name. Operator decides missing/structured value representation and public outcome. 
7. **Retry and caps.** specification/providers.md:430–439 classifies eligibility only; specification/prompts.md:192–199 recommends retry for missing required call but gives no count, delay, storage treatment or remedy for an illicit call under none. Prefer bounded retry before accepting a step, honor supplied retryAfter under a configured budget, never execute forbidden calls or retry completed tool side effects. Operator sets retry budget/backoff and hard cap (infrastructure/runtime.md:109), whether a rejected response counts against that budget or maxSteps, and handling of zero/negative/fractional caps. maxSteps is a per-side count of model cycles, not a tool count; a stop reason may be exposed before durable M1-6 status. Fallback chain selection belongs to M7, distinct from retrying one model.
8. **Usage and metadata.** Finish provides usage, optional metadata lookup can augment logs, and there is no Message.usage (specification/providers.md:354–366,528–548,563–566; specification/threads/messages.md:29). Prefer preserving provider-supplied zeroes and optional fields without assigning invented prices/counts. Operator decides log or message metadata convention, upstreams omitting usage, rejection/timeout of optional metadata and their observability. Blocking between steps violates line 564; awaiting pending callbacks at final settlement satisfies 565.
9. **Reasoning/option merge.** specification/providers.md:245–264 does not specify recursive merge or tie-breaking between equidistant supported levels. Prefer last-wins per top-level key and a deterministic mapping consistent with the package helper. D873–912 carries explicit model levels and optional user, omitted from the page’s request sketch; forward model-declared levels when present. Native effort naming and capability discovery are provider/model specific. Operator decides supported wire dialect; no universal OpenAI-compatible field for arbitrary reasoning or tool extensions.
10. **Credential-free local servers.** specification/providers.md:52–64 and D3550 require a string apiKey in factory config; requiredness of a slot is separately configurable. Prefer allowing an unset slot, supplying an empty string at this boundary and omitting Authorization on that wire request. Operator chooses endpoint defaults, credential sources and redaction of dumped requests. For extensions with createFetch, infrastructure/providers.md:184–189 specifically requires per-request construction with executing state.
11. **Variables.** specification/prompts.md:50,90–91,119–125 and specification/threads.md:220–240 define safety, layering and defaults, not placeholder grammar, argument/env collisions, sanitization algorithm, or position of tool-config env in the five levels. Operator should document syntax, reject unresolved required variables before invoking, forbid secret interpolation, preserve literal text and test tool-specific values without leaking them into unrelated tools. Full mutable/descendant env is M2/M3; the single root can exercise accessible levels today.
12. **Commit frequency and output visibility.** infrastructure/runtime.md:47–50,387 proves durable assistant before execution and results before advancing. Per-tool commits versus one result batch cannot be decided by the numbered phase list alone. Prefer per-result visibility as the project explicitly requires. Spec does not demand persistence of every delta, a synthetic error message on provider failures or a separate durable record for each phase. Status and queue recovery stay with M1-6.
13. **Nested callable and model ownership.** specification/tools.md:44 explicitly distinguishes thrown queue errors and returned invokeTool errors although D529–566 summarizes unlisted calls as throwing. Follow prose for behavior. `uses` limits *user code’s named invocations*; it neither grants model exposure nor substitutes for the prompt tool list. Unknown model tool has no explicit policy; a recoverable linked result fits infrastructure/runtime.md:92. Provider catalog tools are model-specific and can run upstream (specification/providers.md:602–615,653); owner decides whether unsupported tools block setup or are deferred. Never dispatch an upstream result a second time.
