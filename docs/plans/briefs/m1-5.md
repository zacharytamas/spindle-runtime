## 2. Thirteen dispatch contracts

Each row inherits these cited cells. **Arguments** always begin with ThreadState and end with HookExecutionContext (`specification/hooks.md:124–126,514–607`; D5909–5945,6023–6359); only intervening arguments appear below. **Order** for every row is selected prompt list OR fallback agent list (`specification/hooks.md:76–87,99–100`; `specification/prompts.md:272–274`), never both. At rest the latter supplies lifecycle hooks. Select each matching implementation at the trigger; “one” counts the position, not the number of IDs. Multiple IDs of one type are legal (`specification/hooks.md:64`); declaration-order chaining within that list is the plan's reading (part 5). **Throw** in all rows is nonfatal to the decorated turn (`specification/hooks.md:5`); the column adds the effect on the operation. “silent” means the text supplies no rule. **Void** means no replacement, ordinary undefined completion, no specified null contract. **Required** means neither null nor undefined is in the signature; behavior on such an invalid return is silent. S/R = applicability to silent messages / at rest. A dash in S means the operation is not triggered by a message's visibility.

## 3. Black-box scenarios

IDs are printed as their unique digest suffix; combine with the cited page's colon-separated key in `packages/conformance/requirements.json`. “New” refers to the verbatim entries below. MUST includes unconditional behavioral statements and the seven mandatory rows under `specification/threads/messages.md:190`. SHOULD and MAY retain their weaker force. Assert observations per message ID, tool call ID and assembly, including negative observations. A hook may record public state reads and caught API rejections.

1. **MUST · active inject.** Given two sequential tools, when the first awaits injection, then its immediate getMessage and inclusive getMessages agree with the returned transformed row; each create hook observed its ID once, and the second tool and later hook see it chronologically. `specification/threads/messages.md:119–120,134–136,194`; `specification/threads/execution-state.md:45–48` (4fcc1f95,22cf59fa,b74ef581,73bce32e,8254ece3,8cefb16e).
2. **MUST · idle inject.** Given an idle thread and different prompt/agent lifecycle IDs, when the probe injects, then both agent callbacks run with agent provenance and the row is readable before starting a run. `specification/threads/messages.md:117–120,195`; `specification/hooks.md:99–100,194` (a63f8e52,251bf5a2,3b4fc9bc).
3. **MUST · two visibility settings.** Given visible and silent injections, when a pass-through prompt runs, then both persisted, fired lifecycle callbacks and appeared in the raw snapshot, live history and request. Default query omits only the silent one; inclusive query returns both. `specification/threads/messages.md:99,127–130,196`; `specification/threads/execution-state.md:48` (35d60289,bd122f30,b93f89a4,e4ba69e7,da639364,dca92c64).
4. **MUST · request-only edits.** Given identifiable rows, when filter compacts two, drops one, redacts nested metadata in place and appends a synthetic row, then transformation consumes that sequence; prefilter changes provider content in place, provider sees its final array, later live and stored reads still match the original rows. `specification/threads/messages.md:197`; `specification/hooks.md:229–230,262–263`; `specification/threads/execution-state.md:49` (77a09885,d2ff2793,2eca3c1a,5cf7c4b6,a0834ffa,cf4e7ca0).
5. **MUST · filter injection.** Given two model steps, when first filter persists a tagged row and returns its input, then create hooks bracket it, a subsequent hook sees it live, first request lacks it, second snapshot includes it; exactly two assemblies. `specification/threads/messages.md:198`; `specification/hooks.md:227,231,304–306` (1ba43990,62ac4caa,61b94fc9,6d8b1d0c,8a28a42b).
6. **MUST · prefilter injection.** Given the same fixture, when first prefilter injects, then same two lifecycle observations, immediate persisted read, no restarted filter/prefilter, request one excludes it and request two includes it. `specification/threads/messages.md:199`; `specification/hooks.md:264,305–306` (e0078c2e,b7d299a8,000bf2b7).
7. **MUST · system injection.** Given an interpolated include and variable, when the system hook records the rendered text, injects a tagged silent row and returns a replacement, then first filter receives it once in storage shape, prefilter sees its transformed provider shape and returns a distinctive final array; first dispatch includes the replacement system and final history. Repeat with empty string, sync null and async undefined. `specification/hooks.md:212–215,302–303`; `infrastructure/runtime.md:61–73`; `specification/threads/messages.md:200` (b17aee6d,29e645c3,a237deef,a72bbc07,f88b47c5,67885fd3,aa659667,88c209cc,0018442c,14d530a7,babeaaef,bd9fdd64,41fe7364,8233eb0b).
8. **MUST · hook source.** Given prompt lists two filter IDs, agent lists filter and create, plus an installed unused hook, when prompt runs, then see the two prompt markers, correct promptName and no active agent create marker. With empty and omitted lists see agentName and agent callbacks; with neither, no hooks. Observe creation separately before first inbound processing, even with no run. `specification/hooks.md:23,64,76–100,124–126,194–196`; `specification/prompts.md:272–274` (41bdae5c,e6324c34,dce1c8bc,17286533,f66e7c81,f7da5f56,bf795e82,3b4fc9bc).
9. **MUST · writes.** Given inbound human text, scripted assistant text and tool calls, success/error results, and tool/request-hook injections of user, assistant and system messages, when each is inserted, then before sees an ID/time and can stamp metadata; after reads exactly the persisted stamped row. Assistant with calls is readable before tool execution. Given an existing silent row, when active and idle callers update content and metadata, then before receives ID and patch, after receives the stored transformed row; unrelated metadata survives. Exercise any internal pending→completed/failed update if the runtime makes one. `specification/hooks.md:320–321,334,348–349,362`; `specification/threads/messages.md:169–177`; `infrastructure/runtime.md:47–49` (e73207b8,41d77a88,b89bae84,d44aaea6,91bb4c62,c6b52c77,f6fb47da).
10. **SHOULD · write failures.** Given separately throwing before/after hooks, when a tool catches inject/update failure, then a before veto leaves no new row/no changed row and no after callback; after failure leaves the committed insert/update readable. In each case script reaches its next appropriate operation; never replay the successful write. `specification/hooks.md:5,322,335,350,363` (765e84ae,9d7eaeac,e1b53f31,d7e8a202,3d8dede1).
11. **MUST · reasoning.** Given assistant responses with text only, details only, both, neither (including tool-call-only content), when a later request retains them, then read original text/JSON details and compare accepted provider form; default/true include replays, false suppresses both while storage retains them. Remove one assistant first in filter, then in prefilter: its reasoning never appears elsewhere. Select an incompatible provider/model: omit or convert details and read the original stored data again. `specification/threads/messages.md:22–23,73–77`; `specification/prompts.md:237,246–247` (7abccc72,80b5ff9b,b9e3d243,bbc2f60d,c0dc1ab1).
12. **MUST · both outcomes.** Given two calls in one response, when first succeeds and second throws, then record one started and done per ID, success only on first, failure only on second, before-store on both. Have branch callbacks replace success/error text and before-store append a marker; read both final rows and next request. Repeat branch hooks returning null; check originals. Return misleading values from observer hooks via an untyped fixture; tool inputs and stored results stay intact. No crash. `specification/hooks.md:369,381–382,388–393,402–420,432–442`; `infrastructure/runtime.md:88,92` (7bef4e87,295f041d,a91f50b9,20b781d9,565d6e35,ca83d472,6d96f2a3,baf0fc02,83735bf6,732b2d4b).
13. **MUST · stream boundaries** (named-argument early delivery also SHOULD at `specification/tools.md:118`). Given a provider withholding the rest of a call until a hook records its observation, when no progress field is declared, then observe known name and undefined progress before full JSON. When declared, deliver a quoted value over multiple fragments, then hold a long trailing argument: observe the decoded value before releasing the tail. When the named argument never arrives, finish call and observe exactly one start with undefined. `specification/hooks.md:369,377–382`; `specification/tools.md:118–121` (b02bac78,f31fd3d3,bdfd2d2d,3fb4e4f0,106ba9d7; new `specification/tools.md:121`).
14. **MUST · attachments.** Given a tool returning text and an existing AttachmentRef, when success rewrites text preserving refs, then before-store sees both; when it deliberately substitutes another valid ref, stored tool message contains the replacement ref and text. Repeat error branch with an attachment-bearing replacement. Inspect a new binary ToolAttachment at the hook boundary separately; durable binary materialization belongs to `specification/threads/messages.md:3`. `specification/hooks.md:481–490`; `specification/threads/messages.md:21,53–66` (8e371f2b,5fc8a060).
15. **SHOULD · bounded call.** Given a never-settling observational hook, when its configured deadline passes, then a later callback or provider request occurs, exactly one result persists and run completes within a fixture deadline. Also throw an error containing a sentinel secret; any reported error/log must omit the sentinel. `specification/hooks.md:5,66–68` (cb48415f,48c6c25e,3d8dede1). Deadline value and specific log format are product assertions.

16. **MUST · ordinary failures.** Given an observational callback that throws on thread creation, tool start or tool completion, when a normal turn runs, then its input and assistant response are persisted and its scheduled tool actually executes once. Repeat with a throwing result transformer: observe continued operation and a correlated persisted tool result. Only the nonfatal-turn behavior and required writes are conformance assertions; exact fallback contents follow the chosen policy. `specification/hooks.md:5,23,369,432`; `infrastructure/runtime.md:47–49,92` (3d8dede1,41bdae5c,732b2d4b).
17. **MAY · optional request gate.** Given a runtime explicitly configured to treat a request-context hook as a policy gate, when that gate refuses, then the scripted provider receives no request for the blocked assembly; verify a later allowed turn can proceed. `specification/hooks.md:273`; `specification/threads/execution-state.md:113` (no dedicated gate ID; 1a0354bc lists the reason, owned by `specification/threads/messages.md:1`-6).
18. **MUST · accepted inputs and presentation.** Given a public injection for each allowed role (user, assistant, system), when the caller supplies empty-string content, structured metadata and either silent flag, then each successful call returns its own persisted message with its role and content. User denotes B and assistant denotes A independent of caller. A provider-created tool row is legal internally. Public injection of role tool, null content, or queue-only attachments is outside D2101–2110; public updates accept optional string content and object metadata (D2134–2139). Check the public types reject those invalid shapes; no particular JavaScript exception is specified. `specification/threads/messages.md:13–29,117–120,159–160` (8fe975d3,487717df,b74ef581).
19. **MUST · hook-author obligations in fixtures.** Given a content-modifying hook that accepts a declared schema and an external-service hook whose lookup fails, when malformed input or a rejected lookup reaches them, then fixture observations show input validation and graceful failure, with no leaked sensitive input. `specification/hooks.md:68,271,428` (48c6c25e,00bf29ce,e7ff07c0). This demonstrates those hooks' behavior; it cannot certify arbitrary operator hooks.

## 5. Open readings and decisions

1. **Pre-insert identity.** D2006–2022,5947,6120–6132 give hooks a full Message with id and created_at. `specification/hooks.md:320–321` mandates use of the returned object. Either disallow identity rewrites explicitly or persist the returned identity; favor the latter for valid unique IDs and reject invalid/colliding rows. Never show a provisional ID that silently changes after insertion. Validation/collision behavior is an operator decision.
2. **Veto versus essential records.** `specification/hooks.md:322,350` say SHOULD prevent; `specification/hooks.md:5` protects the turn; `infrastructure/runtime.md:47–49,92` require durable assistant/tool/error rows. D's before-create/update comments distinguish rejected public writes from essential internal writes with last good values. Recommend that distinction; preserve the last successful transformation and report the veto to the public caller. For before-store failure prefer last good result. No mandated precise recovery algorithm.
3. **At-rest state and wakeup.** `specification/hooks.md:136,140` say execution is always present; `specification/threads/execution-state.md:3,9–11` and `specification/threads/messages.md:117,195` explicitly support idle hooks. Prefer null at rest, including after_thread_created before execution, and actual execution state for active callbacks. `infrastructure/runtime.md:33,38` describe a user invocation trigger; `specification/threads/messages.md:195` permits injection and read before another execution. Distinguish sending a turn from a raw at-rest state mutation.
4. **Ordering multiple implementations.** `specification/hooks.md:64,76–87` and `infrastructure/runtime.md:161–163` establish selection and composition stages but give no complete algorithm for two parent transforms, duplicate references, or a middle failure. Prefer one pass over selected IDs in declared order, feeding each the last good value; null keeps the value supplied to that callback. Exact-once assembly means one traversal. Decide duplicate-reference and invalid-return policy explicitly; a missing matched type in a nonempty list never re-enables agent fallback.
5. **Tool partial order.** `specification/hooks.md:369–393,402–442` fix start before execution, branch by execution outcome, transformation before storage, done after execution. No text says whether done observes original or rewritten output or runs before/after persistence. Prefer branch transform → before-store transform → message lifecycle/storage → done with final result. Select branch once on the actual tool outcome even if a failure hook recovers. Operator decision on done timing, recovery changing status, and handling invalid arguments/unstreamed invocations (no progress stream to observe).
6. **Request gate and timeout.** `specification/hooks.md:5,66,273` allow a nonfatal decoration and an optional request gate. Recommend default ordinary failures continue with last good input; enable a blocking gate only with explicit operator policy. Choose timeout duration, late side-effect policy and observable error shape. A deadline frees the caller; it cannot promise cancellation of arbitrary user JS. `specification/hooks.md:148`'s signal belongs to the execution.
7. **API surface drift.** `specification/hooks.md:19–36,613` describe fourteen thread hooks. D6023–6359 also includes user_client_attached, user_client_detached, user_value_changed. Dispatch thirteen thread hooks here, reserve one for `specification/threads/messages.md:3`; never index a thread-only dispatch as if all package HookNames were thread callbacks. HookContext is the state alias, final provenance is HookExecutionContext. Use full Message including reasoning/attachments despite `specification/hooks.md:451–462`'s abbreviated shape. D5992 permits multimodal arrays and provider extensions.
8. **Eligible history.** D2594–2598 and filter documentation mention historyLimit; pinned P optional properties and `infrastructure/runtime.md:65–75`/`specification/threads/execution-state.md:45–49` supply no such cap. Use chronological eligible persisted history, including silent rows; no implied default truncation. A product extension needs explicit semantics. Live means later reads reflect successful writes; no specified array-object identity. Preserve stored reasoning across provider conversion, never rehydrate removed reasoning after final filtering (`specification/threads/messages.md:73–77`).
9. **Mutation shape and authority.** `specification/threads/messages.md:7` loosely calls before-create/update non-destructive, but `specification/hooks.md:321,349` explicitly require persistent transformations. D2134 limits public MessageUpdates to content and merged metadata; `specification/hooks.md:344` and the installed hook signature return arbitrary records. ## 6. Store contract

Reviewed `packages/runtime/src/store/ThreadStore.ts` on `origin/m1/3-store` at `56d3c009d290326f0874dd5a6c109304e8dc2651`. These are interface findings; recheck the fix-round head.

1. **No identity-preserving pre-insert contract.** NewMessage includes role and selected writable fields but omits id/created_at; appendMessages returns full rows only after insertion. The interface cannot promise that a complete pre-create hook argument and the inserted row agree on those fields (`specification/hooks.md:320–321`; `specification/threads/messages.md:13,25`). A transaction alone does not supply that contract.
2. **Batch append is narrower than a lifecycle.** Preserve the assistant row before any tool runs, bracket every insert separately, pass actual committed/readable output to after-create, and keep it if that callback fails. Do not place user callbacks or the whole step inside a transaction whose rollback can erase successful writes (`infrastructure/runtime.md:47–49`; `specification/hooks.md:334–335`; `specification/threads/messages.md:120`). One result's hook failure must not remove the preceding assistant record.
3. **Public query defaults are wrong for assembly.** getMessages supports options; use chronological, inclusive reads for the cut at filter start (`specification/threads/messages.md:96–100`; `infrastructure/runtime.md:65–73`). No immutable snapshot token or explicit unbounded-read guarantee appears here. A materialized independent read suffices if complete; test beyond any page default, including equal timestamps and nested mutable data. Ordinary callers retain descending, silent-excluding defaults.
4. **Live history and updates.** No subscription or execution history view on ThreadStore; getMessage/getMessages and returned writes provide readback. Later hooks/tools must see successful inserts, silent records and current persisted content independently of the snapshot. updateMessage accepts MessageUpdates, narrower than before-update's Record. Check metadata merge and after-hook visibility by readback (`specification/threads/execution-state.md:45–49`; `specification/hooks.md:348–363`; D2134). Missing update uses MessageNotFound; no successful after callback.
5. **Tool data and ownership.** NewMessage can carry reasoning strings, prompt, call correlation, tool status and stored attachment refs. It has no field for raw ToolAttachment and no file-materialization operation. Persist supported refs and unchanged reasoning data; conversion for selected model belongs to its request (`specification/hooks.md:490`; `specification/threads/messages.md:73–77`; `infrastructure/runtime.md:82`). No new queue/lease/status operation is required here.
6. **Created thread boundary.** createThread returns durable thread identity; invoke the agent lifecycle callback there before processing input (`specification/hooks.md:23,99–100`). Store Thread contains agentId but no active prompt or hook definitions. Resolution and provenance require the loaded definitions. No need to manufacture a running execution or make store reads trigger hooks.
