## 2. State machines

**Run status.** The current (state, reason) pair governs since. New transitions carry epoch microseconds. Re-reading or reasserting the same pair preserves since. No spec minimum elapsed time or distinct-clock-tick promise (E:84–85,121). Codes below are SHOULD where applicable except the mandatory lost-execution pair. Other raw codes MAY be added (E:107–114).

|From → to|Trigger|Reason|Source|
|---|---|---|---|
|absent → idle|creation, no previous run|explicit null, since 0|E:95|
|idle / failed → running|any execution starts, including recovery|explicit null|E:96,118–120|
|running → running|additional work queued in same run|unchanged null and since|R:38; E:96,121|
|running → idle|text stop, stop tool, park, force human, blocked by hook|stop_on_response, stop_tool, awaiting_human, forced_human_turn, hook_blocked respectively|E:99–103,113|
|running → idle|stopped/cancelled, user abort, terminal tool/session API, total/side/session cap, handler park|aborted, aborted_by_user, session_stop, state_stop_session, max_total_steps, max_side_steps, max_session_turns, handler_idle respectively. Handler/session integration beyond this PR as applicable.|E:107–113|
|running → failed|step exception, repeated tool failure ending run, terminal failure, fatal error|step_error, repeated_tool_error, session_fail, fatal_error. An ordinary tool exception alone is a persisted error result.|E:114,118; R:92|
|running → failed|executor lost|execution_lost (required)|E:120|
|settled → same|read/restart without a new execution|stored reason, stable since|E:119–121|
|running → settled|explicit terminate aborts execution|precise pair silent; recommend idle/aborted for deliberate cancellation|R:230–232; E:113,118|

**Queue entry.** Identity hooks, unlimited history and a prompt recipient in the provider column. “Silent” below denotes a specification gap except when referring to the message field. Eligible records can otherwise be filtered. T:63,119,258; R:33–38,42–50,65–75,219–225; M:145–167.

## 3. Black-box scenarios

ID notation: R, E, T, M, U followed by an eight-digit suffix expands to the corresponding requirement page slug and suffix (e.g. R/0953e887 = infrastructure:runtime:0953e887). “new” points to a quote in part 4. MUST includes operative non-keyword prose, as in the project's curated ledger. SHOULD and MAY retain their force. Local predicates are explicitly identified. 1. **MUST · loss during tool.** Given a committed assistant response with two calls, first completed, second held after externally observable entry, and a later acknowledged queued token, when the owner dies and a surviving process reads status, then report failed/execution_lost. Keep the response and first result exactly as committed; no fabricated success for the second. On recovery retain/deliver pending token in order. Assert no blind repeat of the external effect under the policy in part 5. R:47–49,221–225,387–389; E:119–120. R/f6fb47da,43d5659d,3b19a524; E/77ce1e15,286367b3.

No invented completed response. On a later send observe A running/null then settled, earlier records and x before y in the recovery request. E:95–96,118–121; R:221–225. E/37e4432c,77ce1e15,286367b3; R/34b9e0d8,3b19a524.

## 5. Open readings and recommended decisions

1. **What survives a dead owner?** E:119–120 dictates failed/execution_lost followed by running on later recovery. R:221–225,387–389 requires durable queued work and already committed records. Nothing specifies automatic restart, replay of the model, retry count, completion of an orphan tool call, or exactly-once side effects. H:59–63 assigns exactly-once and no automatic retry to handlers. **Operator decision:** retain undelivered input, surface failed until a deliberate recovery trigger, preserve the committed prefix, never silently repeat a possibly effectful tool. Decide how an unresolved call is represented before sending history to a provider that requires matching results. Do not invent a successful result or throw away the assistant turn. Recovery cannot infer whether a payment/email succeeded from the absence of its result.
2. **Stop, abort and ownership.** E:63–70 and D:2609–2622 distinguish loop stop from abortion of an in-progress model call. Signal firing on ordinary stop during a tool, streaming partial-response disposition, exact stop reason, and what M1-7 displays while it waits are unspecified. Prefer a stop flag at the operation boundary, permit cooperative tool cancellation, preserve completed work; explicit termination signals cancellation immediately. JavaScript promises can ignore a signal and external side effects cannot be rolled back. **Operator decision:** wait for outstanding work or explicitly isolate it; do not admit another flow on a still-running tool merely because its waiter was interrupted. E:70, T:98 and D:2659ff,2998–3010 distinguish stopSession(options?: StopSessionOptions), returning Promise<void>, terminal for the session with optional result, notifyParent and status; execution.stop() returns void. Neither sets the termination timestamp.
