# Spindle message invariants

**Status.** Draft. A reviewer wrote this note from the code at commit `f32f85a`, the settled readings in the milestone 1 plan, and the audit reports of milestone 1. The questions at the end are open. The project's lead has not answered them, and the answers will change this text.

A thread owns a persistent list of messages in SQLite insertion order. A human send appends the inbound message before the run. A successful model step appends one response and then one result per local tool call. Tools and hooks can write between those commits. A provider request reads a snapshot of the list, takes the active side’s perspective, and groups each visible call with its results. Reading the thread afterward still gives insertion order.

## Who may write

- **Loop.** A human send runs agent create hooks at rest. The loop records the accepted response, executes its calls sequentially, and stores each outcome through the same create pipeline. These are the three essential writes in #10. A model retry precedes response insertion. A tool’s external effect and its result row have separate commit points.
- **Tool.** Its ThreadState can inject a user, assistant or system message, update content/metadata, delete a message, or invoke another function tool. Direct invocation returns a ToolResult to the caller. The outer model call owns the required result row. Deleting the active call holder while the tool runs can strand that result (#7–9).
- **Hook.** A transformer may edit its draft or its request input and can independently call the same ThreadState methods. Only the explicit writes enter storage. Nested writes have their own lifecycle. The recursion limit on hook writes measures callback nesting, independently of message.depth. A live hook can delete an earlier essential write or rewrite parentage on creation (#3, #7–10).
- **Idle API caller.** stateAtRest exposes injection, update and delete with execution null. Injection uses agent hooks and resolves after persistence. A retained handle can also write while another handle executes. Such writes participate in #11–15. sendMessage additionally starts a run.
- **Second process.** A runtime using the same database can commit store operations, including edits and deletions. Revision checks see these changes. SQLite serializes individual writes. The M1-5 trigger still permits competing runs across model/tool awaits (#7, #10, #19).

Raw SQL from outside the store is not a supported writer. For example, with SQLite recursive triggers disabled, INSERT OR REPLACE using an existing message ID in a different thread can implicitly delete the old row without firing its delete trigger. The destination revision rises and the source cache can keep serving the missing row (#14–15).

## Gaps in current enforcement

1. **Validation depends on entry point (#1–3, #16–17).** Low-level insertMessage trusts its caller’s ID and time. appendMessages supplies its own ID/time but accepts draft fields directly. Neither applies acceptMessage. A direct insert can supply a NUL ID that Node lists truncated. Typed InjectMessageInput excludes tool and requires string content, but makeThreadState copies role/content without runtime signature validation. Untyped user code can supply role tool without an owner. Contract tests cover the query bound; no end-to-end unsafe hook timestamp case identified.
2. **Parentage and encoding can split a pair (#3, #7–9, #16).** A create hook can assign different parent_id values to a response and its result. Deleting the response then leaves the result. With parents P and Q each listing call x, a result under P arriving after Q’s call is deleted with P but assembled beside Q. requestOrder indexes only x. Also messageRow passes parent_id through without stored(), and a lone surrogate in a call ID can survive escaped inside tool_calls while the scalar tool_call_id normalizes. No end-to-end test identified for these cases.
3. **Other editable create fields carry meaning (#3, #7, #13).** A hook may rename a tool result, change its status, remove returned reasoning or replace the metadata that identifies the reasoning’s model. Locking the call ID and call list protects only part of the relation. The resulting record can disagree with what ran or what the model returned. H12c verifies that the done observer sees the stored version.
4. **Request hooks and destructive APIs can unpair messages (#7–9, #13).** Deleting a result alone leaves the call. Deleting the holder during tool execution lets a later result land alone. Filtering out a result leaves a visible unanswered call; filtering out the holder normally suppresses its result. The final prefilter validates individual provider-message shapes, without checking adjacency, completeness or duplicates across the array. No final pairing check repairs or rejects these requests.
5. **A committed prefix can be incomplete (#7, #9–10, #19).** Kill before the inbound commit leaves no inbound row. After it, during model streaming or before response commit, the inbound row survives without a new model row. After response commit, all announced calls survive. During tool k, the first k−1 results survive and k’s external effect may already have happened. After k’s commit its result survives too. Between steps the completed step survives. Other independently committed hook/tool writes survive at each boundary. M1-5 can display the surviving call on the next request without an answer. S01 tests visibility while running; the current run has neither owner arbitration nor a crash-recovery pairing test covering every boundary.
6. **Revision equality assumes supported writes and exact counts (#14–15).** The raw replacement above escapes source-thread invalidation. Reusing an uncommitted revision would have the same symptom, which is why nested reads cannot seed the cache. The revision is exposed as a JavaScript number. If it exceeds the safe integer range, increment-by-one reasoning needs another representation or a bound. No supported-workload overflow test identified.

## What changes at the next boundaries

- **Queued message entering a run (M1-6).** Restate #5, #10 and #11 around durable admission and delivery. FIFO follows admission sequence even when timestamps tie. A queued item and its eventual history row need one durable delivery decision. Deleting the queue row and crashing before inserting the message loses acknowledged input. Conversely, delivery repeated after a crash duplicates it. Define which pending rows are eligible for the snapshot. Drain before assembly and preserve the queued role, content, attachments, metadata and silent flag. A human recipient parks. An active recipient sees delivery at its next eligible assembly. Fence admission against settlement so one active owner consumes each item and a late arrival still gets a turn. Revision equality checks freshness only. See R:44–49,219–225,237–239 and M:145–167.
- **Lost execution (M1-6).** Restate #7–10 and #19 for a prefix with unanswered calls. Identify the dead owner, settle failed/execution_lost and preserve the committed prefix. On deliberate recovery, give each still-unanswered call one linked error result before dispatch, distinguishing unknown external outcome from tool failure observed in process. A second recovery must find the first repair. A stale owner must be unable to append another result or settle the new run. Never repeat a possibly effectful tool solely because its result is missing. Loss status is specified at E:116–121; the error-result representation is project policy.
- **Two prompt sides (M2).** Restate #6, #9, #11 and #13 for each active side. Each model sees its own turns as assistant and the peer’s turns as user. Each sees only its own call groups and eligible reasoning. Establish the exchange boundary for each handoff. A test should alternate A → B → A with a reused call ID and both sides requesting tools. Assert both requests and the unchanged stored roles. See A:59–66 and R:77–80.
- **Handler side (M2).** Restate #5–7, #10 and #19 for an inbound message delivered to code. Deliver the full persisted message once in persistence order. A handler can inject a reply in its own side’s role or leave no reply. Its invocation contributes zero model steps. A throwing handler leaves the inbound message durable and the next inbound deliverable. Track dispatch so a retry or restart cannot automatically invoke the failed handler again. See E:53–55 and `specification/handlers.md`:26–28,57–75,84.
- **Prompt used as a tool (M2).** Restate #3, #5–9 and #11–13 for nested messages in the same thread. parent_id identifies the enclosing message and depth counts nesting from zero. Establish both from the invocation and use the final persisted parent ID. The inner call and its result share an enclosing parent; the outer call’s single serialized result belongs in the outer scope. Apply the same owner rule for projection, deletion and recovery. Limit each assembly to its eligible scope while preserving chronological thread reads. Exercise siblings that both call x, a nested call x shadowing an outer x, and deletion of each holder. The existing cascade removes sibling result rows matching a call, without traversing a tree of child messages. Define descendant retention explicitly. See M:26–27,100,186, E:34–41 and `specification/prompts.md`:127–131,157–164.

## Questions for the project lead

1. Should create hooks keep control of parent_id and depth when a sub-prompt starts? Today a shape-valid replacement can change either. Reserving them for the runtime would keep the call, result and later delete in the same scope.
2. What should deleting a parent invocation do to its nested conversation? Today deleteMessage removes matching results at the holder’s parent level and leaves descendants. Recursive deletion would remove the nested transcript; retaining it would require a readable ancestry policy after deletion.
3. Should a shape-valid prefilter have the final word on incomplete tool groups? Today its array reaches the provider. An alternative is to reject the offending transformation and use the last group-valid request. The choice determines whether a filter may deliberately discard only a result.
4. Should scalar message text containing a lone surrogate keep today’s U+FFFD normalization? A reversible encoding could preserve the original JavaScript string. Refusing malformed identifiers while retaining normalization for prose would also keep call references comparable.
