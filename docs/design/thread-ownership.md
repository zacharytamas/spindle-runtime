# Thread ownership

## Decisions for the M1-6 fix round

The lead wrote this section on 2026-11-26, after reading the rest of the note. Where it differs from a later section, this section wins. The later sections keep the reasoning and the cases.

**The rule.** A thread has at most one flow. Every write made for an execution names its flow, and the transaction that commits the write checks that the flow still owns the thread. A write from a flow that no longer owns the thread fails with a typed error and changes nothing.

**What is built now.**

1. Every mutation that a tool, a hook, or the loop makes carries the flow, and the store checks it at commit. That covers message inserts, updates, and deletes, key-value writes, queue admissions from inside an execution, terminate from inside an execution, and settlement.
2. A holder is one process. The holder row keeps the holder's id and its process id. An observer that finds the process gone repairs the thread at once. An observer that finds the process alive, or cannot tell, reports the thread as running. Nothing takes over a live process, so there is no lease, no expiry time, and no heartbeat that decides loss. A timer still polls for a terminate or an abort that another process requested. **Operator's choice, question 4.**
3. `spindle recover <thread>` settles a thread whose holder's process is gone, as a status read does, and says so. With `--force` it also settles a thread whose holder is alive, or looks alive, as `failed` with reason `execution_lost`. It is the way out for a frozen process and for a process id that the system gave to another program. It prints what it took over. The writes of the old holder are refused from then on by rule 1.
4. Wall-clock time takes no part in deciding that an execution is lost. It is used for `since` and for record timestamps.
5. An abort does not free the thread while user code of that flow is still running in this process. The flow keeps its claim, and the run status stays `running`, until the last callback has settled. New sends and queued work wait in the queue. When the cleanup finishes, the supervisor settles the run `idle` with the abort's reason and drains the queue as an ordinary settlement does. Three cases end the wait sooner.
   - A terminate settles the run at once as `idle` with `aborted`, as M1-6 already does. Nothing can start on a terminated thread, so there is no second execution to keep out. The writes of the tool that is still running are refused.
   - A process that exits in an orderly way settles its aborting flows as `idle` with the abort's reason before it exits, because its callbacks end with it. `spindle run` after a second Ctrl-C does this.
   - A flow that lost its thread to a recovery no longer holds anything back. The recovery was another process's decision, or the operator's with `--force`, and rule 1 refuses the old flow's writes.

   If the process is killed while it waits, the thread reads `failed` with `execution_lost` and the queue waits for the next trigger. Nothing is persisted to wake it.
6. A handle given to a tool or a hook stops working when that tool or hook returns, rejects, times out, or is aborted. A write that was submitted before that moment and commits after it is checked again at commit, and is refused. **Operator's choice, question 1 of the note.**
7. Recovery decides which calls are open from facts the runtime wrote, never from a field that a hook or user code can change. Two columns on the messages table hold them. `flow_id` is set by the runtime when it inserts a message for an execution. `caller_seq` is set on a tool result and names the message that holds its call. An open call is an entry in the `tool_calls` of a message with the lost flow's id that has no result with that `caller_seq` and that call id. The call id is compared as bytes on both drivers. Request assembly and the delete cascade pair a result with its call through `caller_seq` too.
8. A message that holds an open call of a running flow cannot be deleted. The delete fails with a typed error.
9. A terminated thread accepts one kind of write from outside, an explicit injected message. Updates, deletes, and key-value writes are refused. A handle from before the termination is always refused. **Operator's choice, question 3 of the note.**
10. A tool call is not queued when its arguments hold a known secret. `queueTool` throws, and the error does not print the value. The display fields of a queued attachment are redacted at admission. **Operator's choice, question 2 of the note.**

**What is left out, and why.**

- The call ledger table that the section "Durable facts used to repair a call" proposes. The two columns of decision 7 close the same findings and add no statement per call. The step is already 14 percent slower than its parent against a limit of 20 percent. Milestone 2 can revisit this when nested prompts arrive.
- The process identity domain, with a boot id and a process id namespace. Spindle runs on one machine with one database file, and that is the deployment contract. A database shared between machines is not supported.
- The observation of an unchanged heartbeat counter. Decision 2 replaces it. A heartbeat from the event loop cannot tell a frozen process from one that is busy in synchronous code, and the note says so itself under "Limit of decision 3".
- A persisted wake for work admitted during an abort, and the admission watermark at the step cap. Work that is left queued waits for the next trigger. The run status shows the reason.
- Removing `ThreadStore.transaction` from the interface. The store's own tests use it.

**The step cap.** An execution that reaches the cap ends, even when another stop rule also applies and even when the queue holds work. The stop rules keep their order when the queue is empty, so a response that ends the turn at the cap settles with its own reason. When the queue holds work that the execution would otherwise have gone on to, the thread settles `idle` with reason `max_total_steps`, which tells the operator why that work is still queued. A human send already waiting in the queue counts as the next trigger. It starts a new execution with its own step cap. Work queued by a hook or tool stays queued until a trigger arrives if no sender is waiting.

**Stop.** The loop reads the stop flag at every boundary, which includes after an awaited hook, before entering a tool, and before a retry of a model call. A call that a stop kept from running gets one error result that says it did not run. No hook can change that result's status or its link to the call.

**An unreadable queue entry** is kept with its sequence and its payload, marked as a failed delivery, and skipped. The entries after it are delivered.

## The draft the decisions were taken from

A flow is one execution of one thread. A holder is the supervisor responsible for that flow. Every write carries its origin through to the SQLite transaction that commits it. The store checks that the flow still owns the thread and that the handle that submitted the write is still valid. Losing either check rolls back the whole operation. Only an explicit external operation can act independently of a flow. Releasing a claim, closing its outstanding calls and publishing its final status are one commit.

## What a reader sees

R:239 says “A single thread **MUST NOT** execute multiple concurrent flows.” E:96 defines running as “An execution is in flight. `reason` is `null`.” E:118 requires the runtime to “settle it (`idle` or `failed`) when that execution ends, including when it throws.” Termination is a separate fact. T:471–473 says “Marks the thread inactive and sets `terminated`”, “Aborts in-flight execution”, and “Rejects future `queueMessage()` and execution attempts”. R:231–232 says “abort in-flight work” and “reject future execute/queue/send operations”.

| Condition | Public status | Who owns the thread and what ends that ownership |
|---|---|---|
| At rest | Virgin idle/0/null, otherwise idle with its last reason and time | Nobody. An external admission can atomically claim it. An at-rest hook has authority for its own invocation only. |
| Running | running/null, with the epoch microsecond time of entry | One flow. Ordinary settlement checks the pending queue under the same lock. It can continue that flow or release it. Loss requires a successful repair. |
| Aborting with user code live | Same running triple | The flow retains the claim. Revoke its user handles and stop dispatch immediately. Only runtime cleanup remains. Release after the underlying work settles, or repair on loss. |
| Failed | failed with its reason and time | Nobody. Keep the committed prefix and pending work. A deliberate new trigger can claim it. |
| Terminated | Separate first termination timestamp. At rest preserve the previous triple. In flight keep running/null until cleanup, then idle/aborted, or failed/execution_lost on loss. | No more admissions. A draining flow retains only cleanup authority. After release there is no owner. Repeated external termination returns the original timestamp. |

E:121 says “`since` **MUST** change only when `state` or `reason` changes.” Beats, admissions behind a claim, abort requests and repeated reads preserve it. Epoch time also supplies ordinary record timestamps such as termination time. Its only role in run status is presentation.

A stale flow receives `FlowEnded(terminated|superseded)` in every state, including repeat terminate and settlement. A current but aborting flow's user write receives `FlowAborting`. An expired invocation receives `HookExpired` or `ExecutionEnded`. A genuine external terminal refusal receives `ThreadTerminated`. A child request without a valid parent owner receives `FlowEnded`. Use `CallerHasOpenCalls` for deleting an outstanding caller, regardless of origin. Validation, missing records and SQLite errors retain their own types. Removed methods are statically unavailable. A refused scheduler claim or obsolete recovery observation is normal contention, reported internally as `ClaimUnavailable` or `ObservationChanged` and translated to no work. A holder attempting to drop live claims receives `HolderInUse`. Public `state.setStatus(label)` is distinct: E:122 says it “writes a label into this thread's entry in its parent's subagent registry”. When built, fence the originating flow as part of that write.

M:117 says “The same contract applies during active execution and at rest.” An explicitly external context edit may race a snapshot and still be a valid edit. A flow's captured handle never becomes an external context editor. The terminal injection exception preserves `docs/plans/m1-core-loop.md:884`; it does not authorize a hook saved before termination.

## How an observer establishes loss

Today each supervisor chooses a UUID and keeps its own map (`execution/ThreadSupervisor.ts:120–130`). The migration records wall-clock expiry (`store/migrations/0003_claims.ts:12–24`), and repair selects by that expiry (`store/sqlite.ts:515–535`). Replace that test. E:120 says “A lost execution settles to `failed` with reason `execution_lost`; a later recovery run sets `running` again.”

1. Before claiming, register a fresh, never-reused holder UUID, positive PID, process-identity domain, heartbeat counter zero and silence threshold. Propose retaining the existing 15-second default and one fifth of that interval between beats (`execution/ThreadSupervisor.ts:17–19,273–278`). The holder sets the threshold once. Increment the counter in SQLite from the holder's event loop independently of tool progress. Update an existing registration only. Never resurrect an old UUID. A supervisor renews through abort and shutdown until all of its flows are released. Reconcile its own claimed flows against work reserved for start, running work and outstanding cleanup. A known abandoned local reservation can be repaired by its owner after checking that no work can still start.
2. On status, admission and periodic scans, read the thread and holder together. A settled thread returns its stored triple. For a claimed thread, establish that the observer and holder share a machine, boot and PID namespace before interpreting a PID. Use a deployment-verified domain identifier (for example a host boot ID plus PID namespace identity on Linux). Never infer this from a shared pathname, PID or hostname. A single-host deployment can explicitly guarantee a common namespace. Reject incompatible writer configurations at open. For an unexpected foreign or unverifiable row disable the PID fast path, surface a diagnostic and report running pending administrative verification. Foreign-file sharing is outside the deployment contract.
3. In the same domain, probe the positive PID with signal zero. ESRCH is evidence for immediate repair on the first observation. Success proves only that the PID exists. EPERM cannot establish absence. For both, retain the first local monotonic timestamp at which this observer saw the exact thread, flow, holder and counter. On each read reset the observation if any component or domain changed. The first read returns running. If the same counter is observed again at least the holder's threshold later, it qualifies for repair. Never persist or import another observer's elapsed time. A fresh CLI can catch an absent PID immediately but can report running forever across repeated short-lived invocations of a frozen or reused PID. A persistent supervisor can complete the observation. On unexpected probe errors report running with a diagnostic.
4. Acquire the SQLite writer lock before rereading. Match thread ID, running state, flow UUID, holder UUID, domain, PID, counter and threshold. Re-probe for the immediate-death path, or require the same qualified local observation on the silence path. Re-read the abort and termination markers under the lock. If anything changed, discard the decision and return the newly observed status, repeating observation as needed. If unchanged, close only this flow's open calls, release it, and write failed/execution_lost together. Keep every pending entry. Return the committed status. Neither a status read nor a heartbeat starts a successor. A later admission may claim in a separate transaction. A migration can repair a legacy unowned running row offline; a missing holder for a modern claim is an integrity error, not PID evidence.

| Observation | Consequence |
|---|---|
| PID reused | Signal zero may succeed forever. The new process cannot renew the old UUID. The observing supervisor eventually repairs by unchanged counter. |
| Several supervisors share a PID | Each has its own registration and beat. A live sibling cannot renew an abandoned holder. Share the local live-work guard across supervisors opening the same database. |
| One tool hangs among many threads | If its Promise stays pending and the event loop can beat, this thread reports running forever. Other threads proceed. The heartbeat measures supervisor responsiveness only. |
| SIGSTOP | A peer sees an existing PID and a stationary counter. It may repair after the observation interval. SIGCONT may resume external activity after repair. |
| Synchronous code blocks the holder's event loop | Indistinguishable from SIGSTOP, even if it would have returned a moment later. All threads of that holder are exposed to silence takeover. Prolonged writer contention or scheduling delays can produce the same evidence. |
| Another machine or PID namespace | Unsupported. A local ESRCH is meaningless. Unknown rows report running indefinitely under the policy above. |
| Permission denied | EPERM takes the observation path. Advancing beats keep the thread running. Unchanged beats can qualify only after the full interval. |

On this host, Node 22.22.3 and Bun 1.4.5 both returned true for `process.kill(process.pid, 0)` and threw ESRCH for absent positive PID 2147483647. Signal zero sends no termination signal. Neither runtime's portable probe supplies a process birth token, a namespace match, supervisor progress or proof that a tool stopped. [Node 22 process.kill](https://nodejs.org/docs/latest-v22.x/api/process.html#processkillpid-signal)

**Limit of decision 3.** An existing, slow process whose beat progresses is safe from takeover. No silence threshold can also guarantee that every live slow process is safe. After fallback repair, SQLite admits only the successor's writes, but the old tool may still send mail or charge a card. R:239 does not grant that exception. If physical exclusion is mandatory, disable live-PID takeover until cessation can be established (for example by terminating an isolated executor and observing its exit). That trades automatic recovery of a frozen process for exclusion.

## Abort, terminate, stop and the last admission

Register each callback *before entering it*. Track the settlement of its actual returned Promise, including rejection, independently of the Effect fiber waiting for it. Include nested invokes, timed-out hooks and interrupted provider work. An interruptible wrapper can finish earlier (`execution/tools.ts:105`, `execution/hooks.ts:459–464`, `execution/step.ts:697–704`). Hold a process-wide reservation keyed by database identity and thread until the last registered callback settles. Key by the opened database, including aliases to the same file. Independent isolates in the same process need a shared coordinator or must be excluded as execution hosts for the same file. Detached work which user code never returned cannot be joined.

Abort records a durable request against the flow, closes user write authority, and fires its signal. Termination does this in the transaction that first sets the terminal timestamp. Signal local work immediately after commit; a remote supervisor observes the marker on renewal and before dispatch. Neither request waits for its own calling tool to return: a tool may await terminate. A separate settlement wait joins the underlying work. Cleanup discards late returns, pairs outstanding calls with cancellation errors that distinguish an unknown external outcome, and atomically releases the exact claim. A process that resumes after losing its claim skips cleanup writes and retains the local reservation until its callbacks end. Every local start path, including a new supervisor after remote repair, must consult that reservation before claiming.

External sends and queue calls during ordinary abort enter the durable FIFO; no drain starts while callbacks are live. Preserve a wake for these admissions and claim a fresh flow after abort cleanup, including for a queue-only client that already returned. Persist that wake atomically with abort cleanup and consume it on claim; on startup scan only these explicit wakes, never arbitrary idle pending queues. Claim under the writer lock so competing wakeups have one winner. If the process dies before cleanup, the loss rule takes precedence and a fresh trigger is required. On termination keep prior pending entries inert and reject new sends and queues immediately. A tool that never returns on a responsive holder keeps status running and prevents a successor indefinitely. Other threads remain available. This changes Appendix A's immediate terminal settlement (`docs/plans/m1-core-loop.md:881`).

Ordinary stop means “Stop execution after current operation” (E:63). Set the flow's stop flag without firing an abort signal. Read it before taking an entry, after every awaited hook or other operation, immediately before entering user code, sending a request, or dispatching any retry. A complete response already obtained is stored. Discard an incomplete attempt and suppress its retry. Finish the current tool's receipt. For each issued call stop prevented from starting, write exactly one protected error saying it did not run. Observational hooks may see the result. No result, failure, or create hook may veto, rewrite or relabel that disposition or sever its link. Keep normal settlement and pairing work enabled after stop. The two missed dispatches are at `execution/step.ts:508–519` and `execution/call.ts:389`.

When a completed step reaches the total cap, finalize its receipts and choose idle/max_total_steps before any cooperative stop, response, tool, side or queue-continuation decision (`execution/step.ts:635–655`, `execution/stop-rules.ts:11–37`). Test the cap even on paths that currently return early for stop. A fatal failure or loss before completing a step has its own settlement. The cap leaves all remaining entries pending. A waiter whose admission preceded the cap commit returns the capped status with its entry still pending; it cannot reclaim on that admission. Persist a claim/settlement generation or equivalent admission watermark so even a delayed waiter cannot mistake an intervening settlement for permission to restart. Only a trigger admitted after release may claim. If it arrives first under the writer lock, it queues behind the capped flow. Ordinary successful settlement still checks for pending entries and continues atomically. R:38 says “If a thread is already executing, new work is queued. If idle, the runtime starts a new execution.” The cap is a project exception to automatic continuation, with a visible cost for queue-only callers.

## Handles and commit order

Today normal successful callback return does not set the timeout flag. The bridge checks the owner on entry, and inbound delivery deliberately clears the public execution (`execution/hooks.ts:493–509`, `execution/thread-state.ts:143–168`, `execution/step.ts:368–385`). Give every callback an internal invocation token; give every execution-owned invocation its originating flow even when public `execution` is null. A nested handle inherits all enclosing restrictions. At rest bind the token to the thread's ownership generation and terminal marker, so an intervening claim and release cannot recreate the authority it saw. A genuinely external mutation can begin during a run; any callbacks it invokes carry its scoped external operation and captured generation. They acquire no right to impersonate the running flow.

Proposed lifetime: expire on return, rejection, timeout, abort, or revocation of the parent, whichever comes first. On every write, prepare immutable data and run hooks first. After acquiring the write lock, validate the durable origin and all local tokens again immediately before commit. Serialize token revocation with the final non-yielding write and commit on the token's owning executor. No arbitrary Effect, getter, callback or await may intervene; if the driver cannot provide this section, serialize commits and revocations through a common arbiter and define their order there. Check the monotonic hook deadline even if its timer is delayed. On busy/retry start validation over. In an outer transaction a savepoint release does not count as commit. Carry all originating tokens to the outermost validation, or refuse that composition.

Check the same origin before direct nested tool dispatch (`execution/thread-state.ts:272`, `execution/tools.ts:196`). A durable check cannot undo an external effect started just before takeover. Ownership of future writes still follows the original flow.

## Durable facts used to repair a call

Issue a call when the runtime commits its caller message. In that same transaction insert one runtime-owned row per executable call, keyed by thread, immutable caller sequence and ordinal. Record the issuing flow, full wire call ID as bytes, exact tool name, and the routing facts needed to construct its result (side, prompt attribution, parent and depth). Capture these from dispatch before hooks transform the presentation; bind them to the actual committed caller row after its final ID is chosen. Register siblings before dispatching the first. Do this for queued synthetic callers in the same transaction that removes the pending entry. A user-injected message that resembles a call issues nothing. An uncommitted partial stream issues nothing.

Completion inserts the result message and sets the call row's unique result reference together. Require the matching thread, flow, caller and ordinal, a present caller and an open slot. Make both references foreign keys with compatible deletion rules. Two successive callers may use the same wire ID. Use byte-safe bindings and projections on Node and Bun for identifiers and names, including NUL; never concatenate a tuple with a delimiter. Current repair reads mutable prompt and serialized calls and searches later result IDs (`store/sqlite.ts:113–145`); current result creation passes through hooks (`execution/step.ts:439–457`). Build public call envelopes by masking structured user argument data before serialization. Preserve wire IDs, tool names and structural keys. Use the durable association for deletion and provider pairing as well as repair.

Repair selects only the lost flow's open slots in caller/ordinal order. Insert one system-authored error for each: “The outcome is unknown. Spindle did not run this call again.” Never dispatch it, never alter completed results, never ask a hook to reconstruct a call. A crash between an external action and receipt commit is inherently ambiguous. A second repair sees either the prior running claim with all slots intact or the complete settlement. Refuse caller deletion while any slot is open. Once all are closed, caller deletion may cascade over its exact partners and ledger rows. If direct deletion of a completed result is supported, retain a closed tombstone or delete the complete pair by policy; clearing a result reference must never reopen a call.

## Schema and store changes

- Amend unreleased migration 0003. Replace expiry timestamps with holder identity, domain, positive PID, monotonic integer beat counter and configured threshold. Register before claim. Enforce an existing holder for every new running claim, unique flow IDs, and empty claim fields after release.
- Add ownership generation, durable abort request/reason and the queue wake or watermark needed across settlement. Advance generation on claim, release and first termination. Keep public run state and terminal marker separate. Legacy pre-0003 running rows have no reliable claim or call ledger. During offline migration preserve history and queue, settle them failed/execution_lost, and never guess or replay legacy calls. New guarantees start with ledger-backed issuance.
- Add the call ledger and indexes for open slots by thread and flow. Remove claim_seq as a recovery input. Preserve message revision changes when repair inserts results. For previously unreleased development databases require an explicit migration or a fresh test database, never silently infer trustworthy issuance from editable history.
- Add queue disposition pending/failed_delivery and safe failure category. Select by sequence among pending entries only, including queue length, waiter and continuation checks. Decode and validate one row. For malformed payload or unsupported encoding, compare its thread, sequence and pending disposition under the owning flow, mark failed, retain original bytes and advance. Distinguish operational SQLite errors, which roll back and leave it pending. A well-formed entry for a missing tool gets a normal error partner. Make failed entries inspectable with the same access and masking as the queue. Never print raw rejected payloads.
- Replace optional insert fencing with explicit origin parameters for every mutator. Split registration, renewal, admission, claim, request-abort/terminate, quarantine, call issuance, receipt, conditional repair and release by authority. Keep bulk append atomic or implement via the guarded insert under one outer commit. Remove the unrestricted alternatives in the matrix and migrate probes. A stale settlement fails with the same typed error as a stale insert.
- Synchronous queueTool must return only after commit or throw before acceptance. Snapshot and validate user data before locking, with one read per property. Either reject accessors or handle reentry as an independent call before acquiring the connection. Use a synchronous transaction or refuse contention synchronously without leaving a queued fiber. Suppressing scheduler yields alone cannot cancel a deferred write (`execution/thread-state.ts:163`, `store/sqlite.ts:56,457`). For queueMessage resolve or reject its Promise at the same durability boundary. Loss of a reply after commit remains indeterminate.

## What the next features inherit

- **Handler turn.** Dequeue and identify the owning inbound message once. Invoke under the current flow, track its actual Promise, and fence replies and queued effects. The handler contract says “invoke the handler exactly once for each inbound message on the side's perspective, in message persistence order” (`specification/handlers.md:61`). Ownership serializes delivery; crash-safe exactly-once external action cannot be inferred from it. Persist invocation disposition and treat ambiguous dispatch as indeterminate.
- **Later effect.** Fence scheduling and cancellation with their originating invocation. When the alarm fires it has its own durable delivery identity and external admission. Consume the alarm and admit once in one transaction. A captured scheduling handle grants no authority at firing time.
- **Status endpoint.** Read the persisted triple and separate terminal timestamp through the same observation protocol. An endpoint reading status neither claims pending work nor borrows authority to edit. An endpoint admitting a message uses external admission.
- **Nested prompt.** Share the outer flow, abort signal, step budget and settlement. Give nested invocations their own lifetime and each caller its own slots. Join them before outer release. Never claim the same thread recursively or wait for a queued successor from within its owner.

## Questions for the lead

1. **When does a callback lose its handle?** Expiry at callback return breaks a tool that starts a timer to inject progress, an unawaited nested update, or a hook that hands its state to another callback. Expiry at flow end preserves those patterns but lets a finished tool delete a later turn's history or terminate its still-running flow. At rest there may never be a later flow boundary. Recommend expiry at callback return, plus unconditional timeout and parent revocation. Delayed work should have its own scheduled delivery.
2. **How should queued tool arguments carry a known secret?** Refusal preserves secrecy and exact execution semantics for accepted inputs, but the caller must obtain the secret at execution time. Masking changes the value the tool receives and can silently change an external action. Encryption preserves the value but needs a key outside SQLite, authenticated encryption, restart/rotation rules and protection of failed deliveries. Documenting plaintext like KV preserves compatibility but exposes credentials to every database or backup reader. Recommend typed refusal before persistence with a diagnostic that omits the value. Protect attachment display fields and metadata keys too. Exercise nested JSON with quotes after decoding; a substring check of serialized history misses an escape layer.
3. **May a fresh external editor change a terminated thread?** Appendix A explicitly allows pure injection. Keeping that exception permits an operator to annotate history; extending it to update, delete and KV would permit historical evidence to change. Freezing all writes simplifies archival use but removes the documented injection behavior. Recommend preserving explicit injection and its scoped hooks only, with read-only access for other external operations. Prior flow and hook handles always stay revoked.
