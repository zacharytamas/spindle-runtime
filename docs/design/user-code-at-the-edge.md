# User code at the edge

**Status.** Draft. A reviewer wrote this note from the code at commit `f32f85a`, the settled readings in the milestone 1 plan, and the audit reports of milestone 1. The questions at the end are open. The project's lead has not answered them, and the answers will change this text.

A tool owes its caller a result. A hook owes the operation it decorates a chance to finish. Read what the callback returned while failure can still be attributed to that callback. Keep the last accepted value, refuse an optional write, or record a tool error according to who owns the operation. A handler will own a turn, so its exception belongs to that turn.

## While a definition loads

Definition files execute in the CLI process. They may import modules and await initialization.
Each file and each packed definition loader has 30 seconds to settle. `--load-timeout` sets the limit in seconds for `validate`, `run`, `send`, and `chat`.
Spindle reports a failed or timed-out load and continues checking the other definitions.
A call to `process.exit`, an uncaught exception, or an unhandled rejection during loading also counts as an error.
Spindle listens through one more event-loop turn after loading, then restores the exit function and removes its listeners.
A load error makes validation fail and prevents a run from starting.
A timeout ends the wait. Code that blocks the JavaScript thread can still block the command, and work scheduled by a definition may outlive the load.

## What can cross the boundary

The columns below distinguish these cases in order.

1. Throw an Error, synchronously or by rejecting a promise.
2. Throw another value, including an object whose error description itself throws.
3. Return the wrong shape, including a bad nested field, sparse array, malformed attachment, or disallowed patch key.
4. Return a getter or proxy that throws or changes its answer on a later read.
5. Return data the destination cannot represent, including cycles, nonfinite numbers, exotic objects, functions, excessive nesting, or a new file before a filesystem exists.
6. Change a record's role, call list, correlation, or storage identity. Choose an unsafe, secret, duplicate, or subsequently taken ID.
7. Never settle, including blocking the JavaScript thread.
8. Settle after a deadline, including returning before a delayed timer gets CPU time.
9. Retain a state handle, use it after expiry or interruption, or leave state work running in another promise.
10. Inject or update from inside another write. The nested write can re-enter the same hook.
11. Mutate input in place, including nested data, then fail or return something else.
12. Put a secret into output, keys, diagnostics, an identifier, request history, or an independent output channel.
13. Perform a durable or external action and then fail, lose a race, or be interrupted before the enclosing write commits.

## Failure levels

**One call.** For a model-issued call, reject missing required tool variables, malformed arguments, schema failures and unknown or unoffered names before execution. Persist an error with the original call ID and name, then run the next sibling. Valid schema transforms affect execution arguments. Stored arguments describe the model's call. Direct `invokeTool` returns a result to its caller without inserting a model-call row. A supplied `uses` list restricts it, including an empty list. Hooks have no calling tool and receive an error result from that method. T44, T152–155, R88–92.

**One hook.** Select one whole list, the nonempty prompt list or otherwise the agent list. At rest, including the inbound human write, use the agent list and null execution. Deduplicate by resolved definition and chain in first-listed order. A failed transformer contributes no replacement. Observers cannot revise an event through their return. A successful system hook can return any string, including empty, or keep its input with null or undefined. Only null keeps a success/failure branch result without supplying a replacement. The original tool status selects that branch once. Before-store runs next, followed by create hooks. Done sees the stored result. A started call abandoned during streaming gets one done error and no execution or result row. H70–96, H212–215, H381–392, H400–421, H430–443.

**One write.** A failed before hook rejects an injection or update with `HookFailed`. An insertion collision on an injection raises `MessageIdTaken`. After hooks run after commitment. Their failure cannot undo the row. A hook's successful nested write also survives failure of its enclosing operation. Ordinary promise-returning state methods should reject bad parameters, missing required resources and storage errors, and return null or empty collections for optional absence. Th600–609.

**Essential writes.** The loop needs the persisted human input to start, the actual model response to establish which calls exist, and one answer per call before advancing. Each commits separately. A hook can edit the proposed record, but cannot veto those three writes under the settled rule. Keep role and call list, and keep the result's call ID. A hook can supply a safe unique message ID and nonnegative safe-integer timestamp. Check a replacement ID before handing it to the next hook. If another write takes it before insertion, retry insertion with a fresh UUID, retaining later accepted edits and running no hooks again. An actual storage failure, interruption or implementation gap can still prevent commitment. R40–52, R88–92, H320–335.

**One step or run.** A failed provider attempt stores no model response and executes none of its proposed tools. Eligible failures retry within the step budget (two retries by default). Exhaustion or a nonretryable provider error ends this run with `step_error`. Ordinary typed store errors in the loop also end the run. An invalid definition, an unsupported tool class at setup, a known secret in final system text, or an unexpected defect can end the run with `fatal_error`. An interrupt propagates and signals the execution's abort controller. Earlier commits survive. None of these is evidence that a completed external action can safely run again.

## Gaps at this revision

These are source findings. “No test” means no matching assertion was identified in the inspected suites. A test of an adjacent success path does not establish the missing guarantee.

1. **No bound on a tool or its validator.** A never-settling schema or tool holds all later siblings. The step cap counts completed model steps. A hook timeout releases the waiter for a pending promise, but cannot preempt synchronous code. Its elapsed-time check also precedes validation: a slow getter invoked by the validator can run past the limit. The tool hang was observed in the audit. No test for a deadline that covers acceptance.
2. **The state handle can outlive its owner. ⚑** Appendix A, M1-5 reading 6, and `packages/conformance/DIVERGENCES.md` say every later call rejects with `HookExpired`. Only methods routed through `run` and the live-history getter check. Name listing, `user()` and other simple methods bypass the gate. Shared `context` remains writable. A write admitted before expiration runs independently via `runPromiseWith`, with no commit-time check. Normal settlement and owner interruption do not expire either callback's handle. H15b proves refusal on guarded paths. No test for general revocation or an already-admitted write crossing a turn boundary.
3. **The tool result is only shallowly captured. ⚑** Unlike `acceptResult` for hooks, `storedResult` recognizes a reference by type, ID and path alone. Missing name, MIME type or size can survive storage. A reference with both `data` and reference fields counts in two groups. Its getters can run again in `redactAttachment`, outside the read-error catch. Deep data can fail while redaction walks it before the store raises a typed JSON error. Even the fallback reads the original attachments' length. These escape routes disagree with M1-4 reading 5's promise of a correlated error and continued siblings. Retrying a save after a late JSON error can also repeat pre-create side effects. I2 covers the distinct ID-collision retry. No test for those later reads or repeat side effects on a JSON retry.
4. **Isolation falls back to sharing. ⚑** `hooks.ts`'s `copy` returns its original argument when cloning fails. A result carrying a function in diagnostic data can reach a branch hook before strict validation. That hook can mutate the argument and throw. Keeping the “last good value” then keeps the mutation. A tool can also retain references inside its returned attachments or diagnostics. No test for isolation on clone failure.
5. **The history validators implement different contracts. ⚑** M1-5 reading 4 describes plain JSON. `acceptMessages` clones and uses `every`, which skips holes. Cloneable non-JSON metadata can pass the record check. The prefilter deliberately accepts provider-shaped data and checks dense arrays, including parts and reasoning details. A filter's malformed history can thus appear accepted while entries disappear in projection. I7 checks sparse prefilter output. No corresponding sparse filter test.
6. **Formatting a thrown tool value can itself throw. ⚑** `describe` reads an Error's message outside its try block. Its final string conversion for a non-Error can also fail. Either can escape the promised tool-error conversion. Hook warnings do not inspect the cause. S14 and S14b exercise ordinary throws and result-read errors. No test for a thrown value that defeats diagnostic formatting.
7. **Identity has a wider meaning in the store.** Create hooks can change `parent_id` while preserving role and call ID. The store scopes its delete cascade by parent ID. A result moved to another parent can survive deletion of its model row. Subagent fields on a returned message also lack durable representation in M1. S33b proves a normal cascade. No test for a hook changing the parent of a correlated result.
8. **A completed side effect can lack a receipt.** Model response and tool result are separate commits. A crash or interrupt between them leaves an unanswered call. A hook may already have injected another row or made an external request. The current loop has no durable delivery claim or recovery decision for that interval. The audit observed both sides of the commit boundary. No test establishes recovery without replay. This matters for a handler whose turn must never be automatically redelivered.

## Applying the rule beyond M1

The signature reference is the MIT package at `packages/runtime/node_modules/@standardagents/spec/dist/index.d.ts`, especially `ToolResult` (211), `ToolDefinition` (529), `Effect` (1353), `HandlerDefinition.execute` (5233–5252), `ThreadEndpointHandler` (5508), and `HookSignatures` (6023 onward). The package supplies callable shapes. The pinned pages define what an invocation means.

- **Handler (M2).** Reuse the create/update rows unchanged for writes through state. Like an observer it has no return payload to persist. Its exception policy is unique. Deliver one full persisted inbound message and state to exactly one invocation, in persistence order, with at most one handler in flight per thread. While it runs, later arrivals wait. Returning completes the turn. Throwing fails only that turn: record a runtime-origin failure in the request/execution log, preserve the inbound message and every prior effect, continue the session and deliver the next message fresh. Never auto-redeliver the failed message. There is no model request, step loop, implicit reply, prompt stop rule or session binding. Count the turn toward the exchange cap. A blocking child that needs another message on this thread can deadlock the delivery slot. M2 needs durable admission, ownership and crash semantics, including what ends the lifetime of state work. A timer alone cannot implement delivery. `specification/handlers.md:44–77,79–94`.
- **Scheduled effect.** Reuse tool argument validation and the ordinary write hooks. Like an observer it produces no conversation result. Preserve scheduled arguments and enqueue asynchronously, including after the conversation finishes. Give each job its own state lifetime, cancellation semantics, and a policy for failure and retry consistent with its side effects. The spec recommends inspection, cancellation and idempotence. It does not give effects the handler's exactly-once delivery rule. `specification/effects.md:57–59,81–103`.
- **Thread endpoint.** Reuse at-rest state and the create/update rows. Its return contract is an HTTP Response. Resolve route, thread, access mode and caller before invoking user code. Missing ID is 400, missing thread or route is 404, with the specified error envelope. Authenticated routes require identity and thread access. Public routes still resolve the caller. Execution is null. Preserve a valid handler-produced error response. Define the HTTP disposition of a throw, invalid return or disconnect and the lifetime of any response stream. `specification/threads/endpoints.md:56–69,90–105,107–109,121–133`.
- **Prompt as a tool (M2).** Reuse the caller's tool-event rows, correlation, sequential execution and persisted error/result rules unchanged. Internally it runs a prompt with its own selected hooks and request assembly. Map configured initial message and attachments, shape returned text, calls and errors, and route nested failure to the outer call. Define nesting bounds and cancellation across the two executions. T5–11, T66–79, R88–100, `specification/prompts.md:155–168`.
- **Subagent.** Apply the tool rows to each runtime-injected lifecycle call on a prompt side. Apply the appropriate prompt or handler rules to each child turn. A lifecycle-tool result and the eventual child's outcome are distinct events. Add side-owned relationships, limits, child-local attachments, required parent hooks resolved before creation, parent-side creation observation, and explicit versus implicit completion delivery. Hidden relationships need no exposed tool. These cross-thread effects require ownership and termination rules of their own. T81–95, R115–156, R165–187, R191–217.

## Questions for the project's lead

- **What bounds user-code time?** Today tools wait indefinitely and hooks get 30 seconds per invocation. An alternative is a configurable per-turn budget with separate allowances for callbacks and their outstanding state work. A handler blocked on a child makes a fixed tool-style timeout particularly consequential.
- **When does a state handle expire?** Today ordinary completion leaves it usable, and timeout checks occur at selected entry points. An alternative is an invocation-owned handle that closes on every exit and checks writes again at commit, with an explicit way to obtain at-rest access.
- **What does a stop-tool outcome report?** Today it reads the transformed result before the create hooks, storage downgrade and redaction, then redacts the extracted value. An alternative is to retain pre-redaction property extraction while reporting the status actually stored, as the done observer does.
- **How much recursion is allowed?** Today each nested hook gets its own deadline and writes may go eight levels deep. A total write or time budget for one originating operation would also bound wide chains of shallow writes.
- **Should one start always have one done?** Today a rejected model response closes a streamed start with a synthetic done error. An alternative is to emit done only for executed calls and give clients a separate abandoned-attempt indication. H369, H432–441 leave the unexecuted-start case open.
